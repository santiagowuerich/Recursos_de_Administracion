1.c) Leyes Operacionales Fundamentales

  • Ley de Utilización: U = X · S (La utilización es el producto de la productividad por el tiempo de servicio).
  • Ley de Little: N = X · R (El número de peticiones en el sistema es igual a la productividad por el tiempo de respuesta).
  • Ley del Tiempo de Respuesta Interactivo: R = (N / X) - Z (Donde N es el número de usuarios y Z es el think time).

1.d) Ley de Amdahl

Aceleración Global S = 1 / [ (1 - f) + (f / k) ]
Límite cuando k → ∞: S_max = 1 / (1 - f)

Demuestra que la ganancia de velocidad de un sistema está limitada por la fracción no optimizada (1 - f).

Consigna 2: Ejercicios Prácticos

2.a) Servidor Web Plataforma "Mi Correo"

Datos: T = 30 min = 1.800 s | A = 450 pet | C = 400 pet | B = 28 min = 1.680 s

• Tasa de llegadas (λ) = 450 / 1.800 = 0,25 pet/s (15 pet/min)
• Productividad (X) = 400 / 1.800 = 0,2222 pet/s (13,33 pet/min)
• Utilización (U) = 1.680 / 1.800 = 0,9333 (93,33%)
• Tiempo medio de servicio (S) = 1.680 / 400 = 4,2 s/pet

Impacto: El servidor opera muy saturado (93,33% de utilización). Como λ (0,25) > X (0,22), durante la sesión se acumularon 50 peticiones sin procesar en cola.

2.b) Asistente Virtual "Bruni" (Correo Argentino)

Datos: N = 50 usuarios | Z = 8 s | X = 5 pet/s

R = (N / X) - Z = (50 / 5) - 8 = 10 - 8 = 2 segundos

Impacto: El tiempo medio de respuesta es de 2 segundos, lo cual es óptimo y garantiza una interacción fluida.

2.c) CyberMonday - Pico de Estrés

Datos: N = 200 usuarios | Z = 6 s | X = 5 pet/s (fija)

R = (N / X) - Z = (200 / 5) - 6 = 40 - 6 = 34 segundos

Impacto: Inaceptable. Esperar 34s por mensaje arruina la experiencia y satura el sistema por reintentos. Se requiere escalamiento horizontal (autoscaling de pods) y caché Redis.

2.d) Fluidez en CyberMonday (Objetivo: R = 2 s con N = 200, Z = 6 s)

X = N / (R + Z) = 200 / (2 + 6) = 200 / 8 = 25 peticiones/segundo

Impacto: El backend debe quintuplicar su capacidad (de 5 a 25 pet/s). Se sugiere implementar un pool de al menos 5 réplicas balanceadas.

2.e) Utilización de Segmento de Red Local

Datos: X = 7.500 paq/s | S = 0,01 ms = 0,00001 s/paq

U = X · S = 7.500 · 0,00001 = 0,075 (7,5%)

Impacto: La red opera con una carga muy baja y holgada (7,5%), sin riesgo de congestión.

2.f) Demanda de Servicio en Red 10 Gigabit Ethernet

Datos: BW = 10 Gbps = 10^10 bits/s | Petición: 5 x 1.600 B | Respuesta: 15 x 1.600 B

Total Bytes = (5 + 15) · 1.600 B = 32.000 Bytes = 256.000 bits
Demanda de Servicio (D_red) = 256.000 / 10^10 = 0,0000256 s = 0,0256 ms = 25,6 μs

Impacto: La red 10GbE solo consume 25,6 microsegundos por transacción completa, por lo que nunca será el cuello de botella.

Consigna 3: Caso Aplicado de Monitorización & Benchmarking

Plataforma de Pagos y Facturación Electrónica

Problema: En cierres de mes los tiempos de respuesta suben de 300ms a 12s con errores HTTP 504.

Herramientas: sar (CPU/IO/RAM), pg_stat_statements (PostgreSQL) y sysbench / k6 (Benchmarking OLTP).

Decisiones: Si %iowait > 30% en BD, migrar a discos NVMe, crear índices y agregar Redis. Si saturan conexiones, añadir PgBouncer. Si es CPU en API, activar Autoscaling en Kubernetes.
